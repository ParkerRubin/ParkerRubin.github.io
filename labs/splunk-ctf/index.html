SIEMsational, a Splunk CTF

Splunk, SPL, log investigation

A capture-the-flag challenge from CodePath's CYB102 Splunk Lab. There's no step-by-step guide, just two datasets and a list of questions. You form a hypothesis, write the SPL to prove it, and submit the answer with the search that found it. I answered all 15 questions for the full 20 points: ten warm-ups on a Netflix catalog, then five on a malware investigation in a fictional company's web server logs.

Objective

  • Filter, aggregate and sort log data with SPL to answer specific questions
  • Work with messy fields: multi-value genres, text durations, inconsistent timestamps
  • Trace an attacker across multiple log sources from a single file hash

Part 1: Netflix data

The Netflix set is about getting fluent in the basics: field filters, wildcards, stats count, and sort. A few questions needed more than a filter.

Genres are a list, not a value

A title can sit in several genres at once, stored as one comma-separated string. An exact match on listed_in misses most of them, so wildcards do the work: 

index=main source="*netflix_titles.csv" type="TV Show" listed_in="*Docuseries*"
| stats count

Durations are text

Question 4 looks easy until you notice duration is stored as text like "17 Seasons". Sorting text puts "9 Seasons" above "17 Seasons". Splitting off the number and converting it fixes the sort: 

index=main source="*netflix_titles.csv" type="TV Show"
| eval seasons=tonumber(mvindex(split(duration," "),0))
| sort 0 - seasons | head 1
| table title duration rating

"Which year had the most" is stats, then sort

index=main source="*netflix_titles.csv" type="Movie" rating="G"
| stats count by release_year | sort - count | head 1

Part 2: Investigating the malware

The second dataset is PathCode's web server, authentication and upload logs. The only starting point is an MD5 hash of a known malicious file: 3AADBF7E527FC1A050E1C97FEA1CBA4D.

Who uploaded it

A raw search for the hash across the whole index pointed straight at the uploader's IP, 192.168.1.10. 

index=pathcode 3AADBF7E527FC1A050E1C97FEA1CBA4D

What they tried first

Pivoting on that IP and lining events up by time showed the attacker trying logins as Admin, then Pi, then ABurke, and uploading the file once ABurke worked. Classic credential guessing against common default names before landing on a real account. 

index=pathcode "192.168.1.10" earliest=0 latest=now
| dedup _raw
| table _time source Username Event "User Agent"
| sort _time

The upload log recorded the attacker's user agent as Opera/75.0.3969.218.

Separating the attacker from a real user

Another account, Jmann, uploaded a file from 192.168.1.7 at 15:29, eight minutes after the attacker's upload at 15:21. Pulling both from the upload hashes log showed what each one sent: 

index=pathcode source="*uploadedhashes.csv" (IP="192.168.1.10" OR IP="192.168.1.7")
earliest=0 latest=now
| dedup _raw
| table _time IP _raw
UserIPTimeFile
ABurke (attacker)192.168.1.1015:21EvilScript.exe
Jmann192.168.1.715:29proposal.pdf

EvilScript.exe is the malicious one. It's an executable, it matches the hash from the start of the investigation, and it came from the IP that spent the session guessing passwords. Jmann's upload was a normal user doing normal work that happened to land eight minutes later, which is exactly why you confirm before you blame.

This hash shows up again later in the course. It's the same one VirusTotal identifies as docer.doc, a W97M macro dropper, in my Catalyst IR writeup, where VirusTotal flagged it 48/63.

The gotcha

Partway through, searches that should have returned events came back empty. Clicking into an event's details had quietly locked Splunk's time picker to that one event's timestamp. Adding earliest=0 latest=now to the search forces All Time no matter what the picker says, which is why it's on every Part 2 search above. Adding dedup _raw also cleaned up duplicate rows from the data being indexed more than once.

Tools used

  • Splunk Enterprise in Docker, Search & Reporting
  • SPL: wildcards, stats, sort, eval, split, mvindex, tonumber, dedup, table

Key takeaway

The Netflix half teaches the syntax, the malware half teaches the habit. One hash led to an IP, the IP led to a username trail, and the trail led to a file, all by pivoting on whatever the last search turned up. If I had to pick the most important log field, it's source IP, because it's what ties scattered events across different logs into one story.
