Off Limits, Directory Traversal and Snort Detection

Snort NIDS, packet capture analysis, directory traversal

A full SOC loop from CodePath's CYB102 Snort Lab. Wishful Thinking Inc. runs an old file service that hands back whatever path a client asks for and never checks it. I started on the red side, exploiting the bug to pull files my account was locked out of, then flipped to blue: write a Snort rule that catches it, scope the breach from a packet capture, recommend the fix, and finally beat my own rule.

Objective

  • Exploit a directory traversal to read files outside the service's folder
  • Write a Snort rule that detects the traversal on the wire
  • Prove from a capture exactly which files an attacker reached
  • Recommend the fix at the source plus a defense-in-depth layer

The bug

The service serves files out of /home/student/ftp_folder on port 8888. It takes the requested path, glues it onto that folder, and opens whatever comes out. Nothing stops a request from walking upward with ../. The folder sits three levels below /, so three of them reach the filesystem root: 

GET /../../../etc/shadow

The real problem is who's doing the reading. My shell ran as student, but the service ran as root. File access follows the permissions of the process, not the person asking, so the traversal didn't give me any new privileges. It just talked a root process into reading files for me.

That last one is the punchline. The public general/reports.txt told everyone earnings were up 900%. The file my account was denied said the opposite.

Detecting it with Snort

On the blue side, the traversal has an obvious fingerprint: a literal ../ in a request to port 8888. I added this to local.rules: 

alert tcp any any -> any 8888 (msg:"Directory traversal (../ in a request)"; content:"../"; sid:1000001; rev:1;)

Then replayed the captured attack through it:

snort -c /usr/local/etc/snort/snort.lua -r /opt/snort-lab/project/server.pcapng -A alert_fast

It fired four times, once per traversal request:

Scoping the breach

An alert says something happened. Scope says what it touched. The capture held seven requests, six served and one miss:

RequestResult
/general/reports.txtServed, inside FTP folder
/general/budget.txtServed, inside FTP folder
/../../../etc/os-releaseServed, OUTSIDE
/../../../etc/shadowServed, OUTSIDE
/../../../etc/passwdServed, OUTSIDE
Confidential earnings fileServed, OUTSIDE
/nonexistent.txt404, nothing returned

Four traversal hits, matching the four alerts exactly. Two of them, shadow and the earnings file, are the ones that matter for impact.

Remediation

Fix at the source: canonicalize the path before opening it. Resolve the ../ components with something like path.resolve or realpath, then refuse the request unless the result still sits inside the FTP root. Right now the server just appends the request to its folder and opens whatever that points to.

Defense in depth: stop running the service as root. Run it as an unprivileged user that can't read anything outside its own folder, so even if a traversal bug slips back in, there's nothing sensitive for it to hand over.

Beating my own rule

A rule that matches three literal bytes only catches attackers who don't try. I sent the same request URL-encoded, so ../ never appears on the wire: 

GET /%2e%2e%2f%2e%2e%2f%2e%2e%2fetc/shadow

200 OK, full /etc/shadow back, zero alerts. The server runs decodeURIComponent() on the URL, turning %2e%2e%2f back into ../ after it's already past the sensor. Different bytes on the wire, same traversal on the server. A second rule catches the encoded form, with nocase covering %2E%2E%2F too: 

alert tcp any any -> any 8888 (msg:"Directory traversal (encoded ../)"; content:"%2e%2e%2f"; nocase; sid:1000003; rev:1;)
Even two rules aren't the end of it. Double encoding, mixed encodings and backslashes are all other ways to spell the same thing. That's the real case for the source-side fix: canonicalizing the path catches every spelling, a signature only catches the ones you thought of.

Tools used

  • Snort 3 in Docker, custom local.rules, alert_fast output
  • tcpdump for reading the capture
  • A raw HTTP request script for the traversal and the encoded bypass

Key takeaway

Doing both sides of the same attack made the limits of each obvious. The exploit worked because a root process trusted user input. The first detection worked until I changed how I spelled the attack. Signatures are good for catching the lazy version and for scoping after the fact, but the fix that actually closes the hole lives in the code and in what the service is allowed to touch.
